# 🏛 설계자(Architect) 문서

> 대상: 데이터 모델·수집 범위·확장 방향을 결정하고, 개발자에게 "계약(contract)"을 넘기는 사람.

## 1. 현재 범위 (What's in scope today)

- **자산군**: 국내(한국) **Target Date Fund(TDF)** 만. 펀드명에 `TDF / Target Date / 타겟데이트 / 타깃데이트`
  포함 펀드(클래스 단위, 약 1,900~1,950개)를 전수 수집.
- **소스**: KOFIA 전자공시 `dis.kofia.or.kr` 단일 출처(WebSquare+Proframe XML 게이트웨이).
- **피드 4종**:
  | 지표 | 출처 서비스 | 주기 | 비고 |
  |---|---|---|---|
  | 기준가·설정액·순자산 | `DISFundStdPriceSO` | 영업일 | 1회 벌크 호출로 전 펀드 |
  | 합성총보수(TER)·운용·판매보수 | `DISFundFeeCmsSO` | 월(월말, 1~2개월 시차) | 월말 1회 |
  | 자금흐름(순유입) | (위 설정액에서 **파생**) | 영업일 | Δ설정액. KOFIA 일별 설정/해지 미제공 |
- **저장**: 단일 파일 SQLite. 스키마는 [DATA.md](../../DATA.md) 4절 참조.

## 2. 설계 원칙 (왜 이렇게 만들었나)

1. **변동 지식의 격리** — KOFIA의 서비스ID·`tmpVN` 컬럼 위치·게이트웨이 URL은 바뀔 수 있음.
   이 "변하기 쉬운 모든 것"을 `tdf_crawler/config.py` **한 파일**에 모음. 파서·저장·오케스트레이션은 불변.
2. **순수 함수 파서** — `parsers.py`는 bytes→dataclass 순수 변환(I/O 없음). 픽스처로 100% 오프라인 테스트.
3. **멱등 누적** — 모든 테이블 PK `(fund_code, base_date)` + `ON CONFLICT DO UPDATE`.
   "날짜별 전체 스냅샷"을 시계열로 쌓음 → 재실행/부분실패/중복에 강함.
4. **관측가능성 내장** — `crawl_runs`에 매 실행의 상태/건수/오류 기록(운영·디버깅의 1차 신호).
5. **의존성 최소** — 코어는 표준 라이브러리 + `requests`만. Selenium/bs4는 옵션. (이식성·Docker 경량화)

## 3. 데이터 모델 결정과 트레이드오프 (Decision Log)

| 결정 | 이유 | 트레이드오프 / 향후 재검토 |
|---|---|---|
| 클래스(share class) 단위로 저장 | KOFIA가 클래스별 공시, 코드도 클래스별 | 母-子/클래스 합산 집계는 분석단에서 처리 필요 |
| 설정액·순자산 단위 = **백만원** 원본 보존 | 공시 원단위 그대로(무손실) | 분석 시 단위 인지 필요(원 환산은 ×1e6) |
| 자금흐름 = Δ설정액 **파생** | 일별 설정/해지 공시가 깔끔히 없음 | 실측 설정/해지 공시 추가 시 컬럼 분리 가능 |
| 보수 base_date = 질의 월말 주입 | 보수 행에 날짜 컬럼 없음 | 월 단위 시계열로만 의미 |
| 단일 SQLite | 단순·이식·백업 용이, 규모 충분(연 ~50만행) | 동시 다중 writer/대규모 시 Postgres 고려 |

## 4. 향후 확장 — 엣지케이스 & 로드맵

확장은 대부분 **"새 ServiceSpec + 컬럼맵 + (필요시) 모델/테이블 추가"** 패턴으로 흡수됩니다.
핵심은 config 계약과 스키마 진화를 깨지 않는 것.

### 4.1 수집 범위 확대 (같은 KOFIA, 다른 화면)
- **수익률/등락률**: `DISFundStdPrcRate` 등 → `returns_daily` 테이블 신설(벤치마크 대비 분석 핵심).
- **실측 자금유출입**: 설정/해지 현황 공시 → `flows_daily`의 inflow/outflow 컬럼을 파생 대신 실측으로 채움.
- **연금/ISA/MP/디딤펀드**: 메뉴(`DISMenuSO`)에 별도 서비스 존재. 펀드유형 축 확장.
- **자산배분/글라이드패스**: TDF 핵심 메타. 별도 소스(운용보고서/평가사) 필요 가능.

### 4.2 다른 자산군/국가 (소스 다변화)
- **해외 TDF·다른 국가**: `Fetcher` 추상화는 그대로 두고 **소스별 어댑터(파서+config)** 를 추가.
  `SERVICES`/`*_COLUMNS`를 소스 네임스페이스로 분리(예: `kofia.stdprice`, `sec.xxx`).
- **dedup/식별자 통일**: 국가별 펀드코드 체계 상이 → `funds`에 `source`, `isin` 등 식별 컬럼 도입 검토.

### 4.3 데이터 품질·정규화 (엣지케이스)
- **순자산 0 행**: 재간접/母 클래스에서 다수 → 규모 지표는 설정액 사용을 표준화(분석 문서에 명시).
- **클래스 합산**: 펀드 본질(母펀드) 단위 집계 뷰/머트리얼라이즈드 테이블 제공 고려.
- **보수 누락(母/기관 클래스)**: 정상. NULL 허용 유지.
- **통화/단위 메타**: 컬럼별 단위를 코드/문서에 1급으로 명시(이미 config 주석+DATA.md).
- **휴장일/정정 공시**: 멱등 upsert로 정정 자동 반영. 과거 정정 대량 반영은 `backfill --no-resume`.

### 4.4 스키마 진화 전략
- **컬럼 추가**: nullable로 추가 → 구버전 무중단. (현재 `init_schema`는 `CREATE TABLE IF NOT EXISTS`)
- **본격 마이그레이션 필요 시**: 가벼운 버전 테이블(`schema_meta(version)`) + 단방향 마이그레이션 스크립트 도입 권장.
- **테이블 신설**(returns 등): 기존 PK 규약 `(fund_code, base_date)` 유지로 조인 일관성 확보.

## 5. 비기능 요구 (지켜야 할 속성)
- **재현성**: 같은 입력(날짜) → 같은 결과. 파서 순수성 + 멱등 저장으로 보장.
- **회복탄력성**: 어떤 시점에 죽어도 재실행으로 동일 상태 수렴(운영 문서의 복구 절차).
- **이식성**: 로컬/Docker/리눅스/윈도우 동일 동작. KST 기준일 계산은 컨테이너 TZ와 무관(`today_kst`).
- **관측성**: 모든 실행이 `crawl_runs`에 흔적. 행수 급변은 구조 변경 신호.

## 6. 개발자에게 넘기는 "계약" (변경 시 합의 필요)
- `tdf_crawler/models.py`의 dataclass 필드 = **데이터 모델 계약**. 추가는 자유, 변경/삭제는 분석가 영향.
- `db.py` 스키마 = **저장 계약**. PK 규약 유지.
- 새 피드 추가 = 설계자가 (a) 소스·주기 (b) 모델/테이블 (c) 단위를 정의 → 개발자가 config+parser 구현.
- 변경 영향 범위는 [개발자 문서](../developer/README.md)의 "API 변경 대응"과 함께 검토.
